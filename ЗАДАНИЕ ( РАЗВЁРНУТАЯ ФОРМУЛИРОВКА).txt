Тема ВКР: «Распределённая асинхронная система обработки IoT-событий для мониторинга и управления состоянием помещений»
Актуальность и обоснование темы
Рост числа IoT-устройств на производственных и коммерческих объектах создаёт потребность в системах, способных принимать и обрабатывать поток событий от сотен датчиков в реальном времени. Типичные сценарии — контроль температуры, влажности, задымлённости, уровня освещённости и состояния оборудования в офисных, складских и промышленных помещениях.
Существующие решения (централизованные SCADA-подобные системы, облачные платформы типа AWS IoT Core, Azure IoT Hub) либо ориентированы на конкретного вендора, либо требуют значительных ресурсов для развёртывания и поддержки. При этом многие из них работают в синхронном режиме, что ограничивает пропускную способность при масштабировании на большое число объектов, а также в нештатных сценариях: одновременном срабатывании датчиков движения и задымления, выгрузке накопленных данных после восстановления связи, подключении новых зданий.
Актуальность работы обусловлена необходимостью создания распределённой асинхронной системы, которая обеспечит: упорядоченную доставку событий от датчиков, горизонтальную масштабируемость при росте числа устройств, корректное вычисление текущего состояния помещений, реакцию на аномалии (превышение пороговых значений), а также накопление исторических данных для аналитики и пересчёта состояния.
Применение Apache Kafka как транспорта событий и языка Kotlin для реализации сервисов позволяет построить систему с гарантированной доставкой сообщений, воспроизводимостью потока событий (replay) и возможностью независимого горизонтального масштабирования компонентов — вплоть до обслуживания единой инсталляцией нескольких зданий, разграниченных на уровне топиков и идентификаторов помещений.
Цель и задачи ВКР
Цель работы — проектирование и реализация распределённой асинхронной системы обработки IoT-событий, обеспечивающей мониторинг параметров среды и управление состоянием помещений.
Задачи:

1. Провести обзор существующих систем обработки IoT-событий, сравнить архитектурные подходы (событийная модель, CQRS/Event Sourcing, publish-subscribe), обосновать выбор стека технологий.
2. Спроектировать архитектуру распределённой системы: определить состав сервисов, модель данных, протоколы взаимодействия, топологию топиков Kafka, механизм вычисления агрегированного состояния помещений.
3. Реализовать серверную часть системы на языке Kotlin с использованием Apache Kafka: Event Ingestion Service (приём и валидация событий), State Aggregation Service (вычисление состояния помещений по модели Event Sourcing), Anomaly Detection Service (пороговый алертинг с конфигурируемыми правилами), Query Service (REST API). Реализовать симулятор IoT-шлюза для тестирования.
4. Реализовать хранение исторических данных и механизм пересчёта (replay) состояния из лога событий.
5. Провести тестирование системы: функциональное (корректность агрегации состояния и срабатывания алертов), нагрузочное (пропускная способность в events/sec, средняя задержка обработки), тестирование отказоустойчивости (поведение при недоступности одного из сервисов). Настроить Grafana-дашборды для визуализации результатов мониторинга.
6. Подготовить раздел по безопасности жизнедеятельности.
Технические требования
Для бланка задания на ВКР (краткая формулировка):
Язык реализации — Kotlin (JVM 17+); брокер сообщений — Apache Kafka 3.x; асинхронная обработка событий через consumer groups; горизонтальное масштабирование сервисов; Event Sourcing для вычисления состояния помещений; пороговый алертинг с конфигурируемыми правилами; REST API для чтения состояния и истории; хранение данных в PostgreSQL; контейнеризация (Docker Compose); визуализация в Grafana.
Развёрнутые технические требования:
– Язык программирования: Kotlin (JVM 17+).
– Брокер сообщений: Apache Kafka (не ниже 3.x) с гарантией at-least-once доставки.
– Асинхронная обработка: события от датчиков публикуются в топики Kafka и обрабатываются независимыми консьюмерами без блокировки продюсера.
– Масштабируемость: горизонтальное масштабирование консьюмеров через consumer groups; партиционирование топиков по идентификатору помещения.
– Модель состояния: вычисление текущего состояния помещения путём последовательного применения событий (Event Sourcing); возможность пересчёта состояния из полного лога.
– Обнаружение аномалий: пороговый контроль параметров (температура, влажность, CO₂, задымлённость) с генерацией Alert-событий при превышении правил; правила хранятся в конфигурационном YAML (не hardcode); алерты сохраняются в PostgreSQL и публикуются в отдельный Kafka-топик.
– Хранение данных: реляционная СУБД (PostgreSQL) для агрегированного состояния; Kafka как долговременное хранилище лога событий (retention policy — настраиваемый).
– REST API (Query Service): GET /rooms — текущее состояние всех помещений; GET /rooms/{id}/history?from=&to= — история показаний за период; GET /alerts?active=true — список активных алертов. API доступен внешним клиентам (Grafana, мобильное приложение, другие системы).
– Контейнеризация: Docker-образы для каждого сервиса; Docker Compose для локального развёртывания.
– Покрытие тестами: юнит-тесты, интеграционные тесты с Testcontainers (Kafka, PostgreSQL).
– Визуализация: Grafana подключается к PostgreSQL и отображает дашборды с историей показаний по помещениям, текущим состоянием и алертами. Разработка Grafana-дашбордов не входит в scope ВКР — используется как готовый инструмент.

Архитектура системы (общая схема)
Система состоит из четырёх уровней, разграниченных по зоне ответственности.
Уровень 1 — физические датчики (вне scope ВКР)
Сенсоры температуры (DS18B20), влажности (DHT22), CO₂ (MH-Z19), движения (PIR), освещённости (BH1750). Выдают аналоговый сигнал или байты по I²C/1-Wire. ВКР не затрагивает прошивку и электрическую часть.
Уровень 2 — IoT-шлюз (вне scope ВКР, в работе симулируется)
Микроконтроллер или одноплатный компьютер (ESP32, Raspberry Pi) считывает показания датчиков, упаковывает в JSON и отправляет HTTP POST на Ingestion Service. В рамках ВКР роль шлюза выполняет симулятор — Kotlin-скрипт, генерирующий реалистичный поток событий вида: { "room_id": "A101", "sensor_type": "temperature", "value": 24.3, "timestamp": "..." }.
Уровень 3 — серверная часть (scope ВКР, реализуется на Kotlin)
Включает четыре микросервиса и общую инфраструктуру.
Event Ingestion Service
Принимает HTTP POST /events от шлюзов, проверяет схему события (типы датчиков, диапазоны значений, формат timestamp), публикует валидное событие в Kafka-топик sensor-raw-events. Является единственной точкой входа в систему. Масштабируется горизонтально: несколько экземпляров за балансировщиком нагрузки.
State Aggregation Service
Kafka consumer, читает из sensor-raw-events. Вычисляет текущее состояние каждой комнаты: агрегирует последние показания всех датчиков в объект RoomState. Использует модель Event Sourcing: текущее состояние комнаты не хранится как обновляемая запись, а вычисляется последовательным применением всех событий из лога Kafka. Это обеспечивает возможность пересчёта состояния на любой момент времени (replay) и упрощает восстановление после сбоя. Сохраняет состояние в PostgreSQL (таблица room_states) и публикует обновление в топик room-state-events. Партиционирование по room_id обеспечивает горизонтальное масштабирование без конфликтов записи.
Anomaly Detection Service
Kafka consumer, читает из sensor-raw-events параллельно с State Aggregation. Проверяет пороговые правила, хранящиеся в конфигурационном YAML (например: температура > 35°C, CO₂ > 1500 ppm, задымлённость выше нормы). При срабатывании правила создаёт Alert-запись в PostgreSQL (таблица alerts) и публикует событие в топик alert-events. Масштабируется горизонтально.
Query Service (REST API)
Stateless REST-сервис, читает только из PostgreSQL. Предоставляет эндпоинты: GET /rooms — текущее состояние всех помещений; GET /rooms/{id}/history?from=&to= — история показаний за период; GET /alerts?active=true — активные алерты. Масштабируется горизонтально как stateless-сервис.
Уровень 4 — инфраструктура и визуализация (конфигурируется, не разрабатывается)
Apache Kafka (3.x) — брокер сообщений и персистентный лог событий; PostgreSQL — хранение агрегированного состояния и истории алертов (схема БД разрабатывается в ВКР); Docker Compose — оркестрация всех компонентов локального стенда; Grafana — подключается к PostgreSQL, отображает дашборды с историей показаний, текущим состоянием комнат и алертами. Grafana используется как готовый инструмент визуализации — её разработка не входит в scope ВКР.
Граница ответственности ВКР
В ВКР разрабатываются: четыре Kotlin-сервиса (Ingestion, State Aggregation, Anomaly Detection, Query Service), схема базы данных PostgreSQL (DDL, индексы, миграции), конфигурация Docker Compose, симулятор шлюза, конфигурация пороговых правил для Anomaly Detection.
Вне scope ВКР (используется как готовое ПО или оборудование): прошивка ESP32/RPi, физические датчики, Apache Kafka как брокер, PostgreSQL как СУБД, Grafana как инструмент визуализации, механизмы push-уведомлений, управление исполнительными механизмами (актуаторами).
