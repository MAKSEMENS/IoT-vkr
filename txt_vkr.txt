Объектом работы является распределённая система обработки событий от IoT-датчиков для наблюдения за состоянием помещений (температура, влажность, движение и др.).
Цель работы — спроектировать и реализовать серверную часть такой системы, которая принимает события от датчиков, вычисляет текущее состояние каждого помещения, выявляет отклонения от заданных порогов, отправляет уведомления об этих отклонениях и предоставляет данные внешним приложениям.
Система написана на языке Kotlin. Для обмена сообщениями между частями системы применяется распределённый брокер Apache Kafka, который сохраняет полную историю событий и допускает её повторное чтение. Программа разделена на четыре независимых сервиса: приём и проверка входящих событий, вычисление текущего состояния помещения по полной истории показаний, обнаружение отклонений от заданных порогов и предоставление данных по программному интерфейсу. Сообщения распределяются по идентификатору помещения, что сохраняет порядок их обработки и позволяет наращивать число обработчиков по мере роста нагрузки. Хранилищем служит реляционная база данных PostgreSQL.
Результатом работы является работоспособный прототип, развёрнутый в контейнерах. Функциональное тестирование выполнено с запуском настоящих экземпляров брокера сообщений и базы данных в тестовых контейнерах (Testcontainers). Надёжность обработки достигается тем, что каждое сообщение гарантированно обрабатывается хотя бы один раз, невалидные сообщения отправляются в отдельную очередь и не блокируют поток, а полное состояние любого помещения может быть восстановлено повторным проигрыванием истории событий. 


ABSTRACT
The subject of the work is a distributed system for processing events from IoT sensors in monitored rooms (temperature, humidity, motion and the like).
The goal is to design and implement the backend of such a system: receive events from sensors, maintain the current state of every room, detect deviations from configured thresholds, and expose the data to external applications.
The system is written in Kotlin. Apache Kafka is used as the message broker, which stores the full history of events and allows it to be re-read. The software is split into four independent services: ingestion and validation of incoming events, computation of the current room state from the full history of readings, detection of deviations against configured thresholds, and a programming interface that returns the data on request. Messages are distributed by room identifier, which preserves processing order and lets the number of processors grow with the load. PostgreSQL serves as the storage, and all services are launched together as containers.
The result is a working prototype deployed in containers. Functional testing was carried out with real instances of the message broker and the database running in disposable containers. The tests confirmed correct state computation, proper alert triggering, and resilience to duplicate delivery of the same message. Reliable processing is achieved by guaranteeing that every message is processed at least once, by routing problematic messages to a separate queue so they do not block the stream, and by being able to fully reconstruct any room's state by re-playing the history of events.

ВВЕДЕНИЕ
Распространение IoT-устройств на офисных, складских и промышленных объектах привело к тому, что задачи мониторинга параметров среды решаются десятками и сотнями датчиков на одно здание. Системы такого класса непрерывно собирают показания температуры, влажности, концентрации CO₂, задымлённости и движения, и должны принимать поток событий без потерь, сохранять полную историю для ретроспективного анализа и оперативно реагировать на отклонения. Типовое здание с пятидесятью помещениями формирует порядка двух с половиной миллионов событий в сутки, что предъявляет к серверной части требования по пропускной способности, упорядоченной обработке и устойчивости к сбоям отдельных компонентов.
Существующие решения делятся на три категории. Промышленные SCADA-системы надёжны, но избыточны для офисных объектов и плохо масштабируются. Облачные платформы (AWS IoT Core, Azure IoT Hub) предлагают полный стек, однако создают зависимость от вендора и скрывают внутреннюю логику обработки за управляемыми сервисами. Готовые открытые платформы (ThingsBoard и подобные) ограничивают тонкую настройку логики обработки рамками собственных абстракций. Большинство классических решений работают синхронно, что ограничивает пропускную способность при одновременном срабатывании множества датчиков и при восстановлении соединения после сбоя.
Настоящая работа посвящена проектированию и реализации серверной части распределённой асинхронной системы обработки IoT-событий, которая выполняет приём данных от шлюзов, агрегацию состояния помещений, обнаружение аномалий и предоставление данных через REST API. Зона ответственности системы охватывает следующие уровни IoT-архитектуры — внутрисерверный транспорт, валидацию, хранение, аналитику и интерфейс представления. Физический сбор показаний, обработка на периферии и транспорт до бэкенда остаются за границей системы. Программное обеспечение написано на языке Kotlin. В качестве транспортной шины применяется Apache Kafka, что обеспечивает упорядоченную доставку событий в пределах одного помещения, горизонтальную масштабируемость потребителей и возможность повторного чтения полного лога для пересчёта состояния.
Цель работы — спроектировать и реализовать распределённую асинхронную систему, которая принимает события от IoT-датчиков, вычисляет агрегированное состояние помещений, обнаруживает аномалии и отдаёт данные через REST API. Обеспечить точки подключения для вышележащих слоёв системы — уведомлений, дашбордов и операторских интерфейсов.

1 Обзор предметной области и существующих решений
1.1 Задачи мониторинга IoT-событий в помещениях
Под мониторингом параметров среды понимается непрерывный сбор показаний физических датчиков — температуры, влажности, концентрации CO₂, задымлённости, освещённости, движения — и их обработка на серверной стороне. Такие системы применяются на объектах, где необходим контроль условий в реальном времени: серверные комнаты, склады, производственные цеха, офисные здания.
Типовой набор датчиков для офисного или складского здания включает несколько категорий. Датчики температуры (DS18B20, DHT22) фиксируют изменения с точностью до 0,5 °C и передают показания каждые 5–30 секунд. Датчики влажности часто совмещены с температурными (DHT22 измеряет оба параметра). Датчики CO₂ (MH-Z19, SenseAir S8) используют метод недисперсионной инфракрасной спектроскопии (NDIR) и обновляют показания раз в 2–5 секунд. Датчики задымлённости формируют бинарный сигнал (норма/тревога), но в продвинутых моделях передают числовое значение оптической плотности. Датчики движения (PIR) регистрируют изменение инфракрасного фона в зоне обнаружения. Датчики освещённости (BH1750) измеряют интенсивность света в люксах.
Для оценки масштаба задачи рассмотрим типовое здание с 50 помещениями, в каждом из которых установлены 4–6 датчиков. При частоте опроса раз в 10 секунд суммарный поток составляет 1 200–1 800 событий в минуту, или порядка 2,5 миллионов событий в сутки. На промышленном объекте с сотнями контролируемых зон эта цифра возрастает на порядок. Система должна принимать такой поток без потерь, сохранять полную историю для анализа и при этом обеспечивать время реакции на аномалию в пределах единиц секунд.
Задачи мониторинга разнородны. Часть из них связана с поддержанием допустимых условий: не допустить перегрева серверной выше 30–35 °C, контролировать температурный режим на складе. Другая часть требует оперативной реакции на аварии: резкий скачок CO₂ или срабатывание датчика задымлённости должны приводить к оповещению за секунды, а не за минуты. Накопленная история показаний используется для ретроспективного анализа: систематический перегрев помещения после обеда даёт основание пересмотреть работу системы кондиционирования.
Обработка потока IoT-событий отличается от типовых веб-приложений. Поток непрерывен: датчики отправляют показания каждые 5–30 секунд, и система должна принимать их без потерь даже при кратковременных перегрузках. Порядок событий в рамках одного помещения тоже имеет значение: если термометр последовательно отправил 24.0, 25.5 и 27.0 °C, текущее состояние должно отражать именно 27.0 °C, а не промежуточное значение, задержавшееся из-за сетевого сбоя. Наконец, выход из строя одного компонента не должен приводить к потере данных: события, принятые до сбоя, должны сохраняться и дообрабатываться после восстановления.
1.2 Обзор существующих решений
Существующие решения для обработки данных от IoT-датчиков можно условно разбить на промышленные SCADA-системы, облачные платформы и решения на базе открытого ПО. Ниже рассмотрены представители каждой группы.
SCADA-системы ориентированы на промышленные объекты и работают с протоколами Modbus, OPC UA, BACnet. Они надёжны и сертифицированы для критически важных объектов, но избыточны для задач мониторинга офисных и коммерческих помещений: им требуется специализированное оборудование, сложная настройка, и работают они, как правило, в синхронном режиме, что ограничивает масштабируемость.
Среди наиболее распространённых SCADA-решений можно отметить Wonderware InTouch, Siemens WinCC, Schneider Electric ClearSCADA и отечественные MasterSCADA и TRACE MODE. Эти продукты предоставляют визуализацию через мнемосхемы, архивирование параметров и встроенные механизмы тревог. Однако их лицензионная модель предполагает оплату за количество тегов (контролируемых переменных), что делает стоимость развёртывания существенной для крупных объектов. Кроме того, серверная часть большинства SCADA работает под управлением Windows, а клиентские модули нередко используют устаревшие технологии (ActiveX), что затрудняет доступ с мобильных устройств и из-за пределов локальной сети.
Облачные IoT-платформы (AWS IoT Core, Azure IoT Hub, Google Cloud IoT) предлагают полный стек от приёма телеметрии до аналитики. AWS IoT Core поддерживает MQTT и HTTP, интегрируется с DynamoDB, Kinesis и Lambda. Azure IoT Hub предоставляет управление устройствами и маршрутизацию сообщений. Преимущества — масштабируемость и отсутствие необходимости поддерживать инфраструктуру. Ограничения: привязка к конкретному облачному провайдеру (vendor lock-in), стоимость, растущая с объёмом данных, зависимость от интернет-канала и ограниченный контроль над внутренней логикой обработки.
Помимо перечисленных ограничений, облачные платформы накладывают собственные правила на формат данных и маршрутизацию сообщений. AWS IoT Core, например, использует собственный язык SQL-подобных правил для фильтрации и трансформации потоков, а обработка событий привязана к экосистеме Lambda и Kinesis. Миграция обработки на другого провайдера требует переписывания интеграционного слоя. Для учебного прототипа, который должен демонстрировать внутреннюю логику обработки (а не скрывать её за управляемым сервисом), облачная платформа не подходит: студент не может продемонстрировать на защите код маршрутизации сообщений, если он реализован внутри проприетарного сервиса.
Решения на открытом ПО — ThingsBoard (Java, поддержка MQTT/CoAP/HTTP, хранилище на Cassandra или PostgreSQL), Eclipse Mosquitto (MQTT-брокер), связки Kafka + Kafka Streams для потоковой обработки. Достоинства — развёртывание на собственном оборудовании и полный контроль над логикой. Недостаток — необходимость самостоятельной интеграции компонентов.
ThingsBoard заслуживает отдельного рассмотрения как наиболее функциональная открытая платформа. В ней есть визуальный конструктор правил (Rule Chain), встроенное хранилище телеметрии, управление устройствами и дашборды. Для небольших инсталляций ThingsBoard может быть достаточно. Однако при необходимости тонкой настройки логики обработки (например, собственной стратегии replay или специфических правил агрегации) пользователь оказывается ограничен абстракциями платформы. В настоящей работе вместо готовой платформы используются отдельные компоненты — Kafka, PostgreSQL, Spring Boot, — что делает каждое архитектурное решение явным и пригодным для разбора на защите.

1.3 Уровни IoT-архитектуры и зона ответственности системы
Архитектура промышленного интернета вещей (IIoT) включает 12 уровней — от физических датчиков на периферии до аналитики и интерфейсов в облаке [1]. 
Каждый уровень решает свою задачу: сбор данных, первичная обработка, передача, маршрутизация, хранение, анализ и представление результатов. Не все уровни входят в зону ответственности одной системы — разработчик выбирает, какие слои реализовать, а какие оставить внешним компонентам.
Нижние шесть уровней отвечают за сбор и первичную передачу данных (в разрабатываемой системе они считаются внешними — данные поступают уже в виде HTTP-запросов с JSON-телом, для разработки и тестирования будет использоваться эмулятор шлюза):
1) физический (Physical Layer) — конечные устройства: датчики температуры, влажности, CO₂, движения и др.;
2) периферийные вычисления (Edge Layer) — микроконтроллеры (Raspberry Pi, Arduino), АЦП/ЦАП, первичная обработка сигналов;
3) локальная сеть (Local Network Layer) — передача данных до шлюза по протоколам ZigBee, BLE, LoRa, WiFi;
4) шлюз (Gateway Layer) — ETL-операции на периферии, агрегация данных от группы датчиков, локальная реакция на критические события;
5) внешняя связь (Wide Network Layer) — транспорт между периферией и бэкендом (протоколы LwM2M, CoAP, DTLS);
6) безопасность (Security Layer) — аутентификация, авторизация и шифрование на границе периферии и облака.
Разрабатываемая система покрывает верхние уровни архитектуры:
• уровень внутрисерверной связи (Middleware) — Apache Kafka как брокер сообщений, обеспечивающий асинхронную передачу, буферизацию и маршрутизацию потока событий между микросервисами;
• уровень сбора, обработки и хранения данных (ETL) — event-ingestion-service принимает и валидирует входящие события, state-aggregation-service ведёт полный лог и агрегирует состояние помещений в PostgreSQL;
• уровень аналитики — anomaly-detection-service прогоняет поток событий через набор пороговых правил и формирует алерты при обнаружении отклонений;
• уровень уведомлений — топик alert-events предоставляет готовую точку подключения для сервиса рассылки (e-mail, SMS), который может быть добавлен как отдельный потребитель Kafka;
• уровень представления — query-service предоставляет REST API для отображения текущего состояния помещений, истории показаний и списка алертов.
Таким образом, система принимает данные «на входе» в виде готовых JSON-событий от шлюзов и отвечает за весь бэкенд-цикл: валидацию, маршрутизацию, хранение, агрегацию, обнаружение аномалий и предоставление данных через API. Физический сбор показаний, первичная обработка на периферии и транспорт до бэкенда остаются за границей системы.
Обработка потока IoT-событий отличается от типовых веб-приложений по нескольким параметрам:
• поток непрерывен — датчики отправляют показания каждые 5–30 секунд, и система должна справляться с нагрузкой без потерь;
• порядок обработки важен — показания одного помещения нужно агрегировать последовательно, иначе состояние может оказаться рассогласованным;
• данные привязаны ко времени — показания суточной давности не имеют оперативной ценности для срабатывания алертов, хотя полезны для ретроспективного анализа;
• отдельные датчики могут временно выходить из строя или отправлять заведомо некорректные значения (например, температура −100 °C), и система должна корректно обрабатывать такие ситуации, не останавливая обработку остального потока.
1.4 Архитектурные подходы к обработке потоковых данных
Проектирование системы обработки IoT-событий начинается с двух вопросов: как компоненты взаимодействуют между собой (синхронно или асинхронно) и как хранится и вычисляется состояние помещений.
Синхронная архитектура предполагает, что запрос от датчика обрабатывается в рамках одного HTTP-цикла: данные принимаются, валидируются, записываются в базу и подтверждаются отправителю. Такой подход прост в реализации, но имеет ряд недостатков для IoT-сценариев. Время ответа определяется самым медленным звеном цепочки (обычно записью в БД). При росте числа датчиков или кратковременном сбое базы данных входная точка блокируется, что приводит к отказу в обслуживании. Масштабирование требует увеличения ресурсов каждого компонента одновременно.
Асинхронная архитектура на основе брокера сообщений разделяет приём события и его обработку. Продюсер (точка приёма) публикует событие в очередь и сразу возвращает подтверждение клиенту. Потребители обрабатывают события из очереди в своём темпе. Из этого следует, что точка приёма не блокируется на обработке и отвечает быстро. Если потребитель временно упал, события не теряются: они лежат в брокере и дообрабатываются после восстановления. Разные виды обработки (агрегация состояния, проверка пороговых правил) выполняются параллельно и масштабируются независимо друг от друга.
Асинхронная модель реализуется через паттерн publish-subscribe (pub/sub): продюсер публикует сообщение в именованный топик, а подписанные на него потребители получают копию сообщения независимо друг от друга. В отличие от модели point-to-point (одна очередь — один получатель), pub/sub позволяет нескольким потребителям обрабатывать один и тот же поток событий для разных целей: один потребитель агрегирует состояние помещений, другой — проверяет пороговые правила. При этом каждый потребитель ведёт собственный указатель (offset) в логе и продвигается по нему в своём темпе.
Event Sourcing — подход к хранению состояния, при котором источником истины является полный лог событий, а текущее состояние вычисляется путём последовательного применения всех событий из лога. Применительно к IoT-мониторингу это означает, что состояние помещения (текущая температура, влажность и т.д.) не хранится как обновляемая запись, а пересчитывается из истории показаний. Такой подход позволяет восстановить состояние на любой момент времени (replay), даёт полную аудитируемость и устойчивость к сбоям: если сервис агрегации упал, после перезапуска он продолжит обработку с последнего зафиксированного offset. Плата за это — холодный старт (полный replay) занимает время, пропорциональное объёму лога.
Event Sourcing часто применяется совместно с паттерном CQRS (Command Query Responsibility Segregation), при котором модель записи (приём и сохранение событий) и модель чтения (выдача текущего состояния) разделены. В разрабатываемой системе это разделение реализовано явно: запись производится сервисом агрегации (state-aggregation), а чтение — отдельным REST-сервисом (query-service), обращающимся к PostgreSQL. Благодаря этому каждую сторону можно оптимизировать отдельно: модель записи заточена на последовательную обработку потока, модель чтения — на диапазонные запросы по времени.
В разрабатываемой системе роль персистентного лога событий выполняет Apache Kafka. Партиционирование топиков по идентификатору помещения (room_id) гарантирует, что все события одного помещения обрабатываются одним потребителем в порядке поступления. Конфликтов записи при этом не возникает, а горизонтальное масштабирование сводится к добавлению партиций и экземпляров потребителей: пропускная способность растёт, логика остаётся прежней.
При использовании брокера сообщений нужно учитывать ситуации, когда потребитель не может обработать сообщение (например, из-за некорректных данных или временной недоступности базы). Для таких случаев применяется паттерн Dead Letter Queue (DLQ): после фиксированного числа повторных попыток (retry) необработанное сообщение перенаправляется в отдельный топик-«кладбище» и не блокирует обработку остальных событий в партиции. Каждое событие при этом гарантированно обработано хотя бы раз (at-least-once), а потребитель не зависает на «отравленном» сообщении.
1.5 Обоснование выбора технологического стека
Исходя из сформулированных требований — высокой пропускной способности, необходимости хранения полного журнала событий и возможности горизонтального масштабирования — для реализации системы выбран следующий технологический стек.
В качестве основного языка программирования выбран Kotlin (платформа JVM 17), который обеспечивает безопасность работы с null-значениями, поддержку легковесных потоков (корутин) и полную совместимость с экосистемой Java. По сравнению с Java, Kotlin позволяет писать более лаконичный код за счёт использования классов данных, функций-расширений и удобного синтаксиса, что существенно сокращает объём шаблонного кода. Язык компилируется в байт-код виртуальной машины Java и может использовать любые существующие Java-библиотеки. Согласно опросу JetBrains Developer Ecosystem Survey 2023, Kotlin входит в тройку самых быстрорастущих языков для платформы JVM.
Для разработки микросервисной архитектуры используется фреймворк Spring Boot 3.x. В нём из коробки доступна работа с брокером сообщений, объектно-реляционным отображением (JPA) и REST-интерфейсами. Фреймворк автоматизирует начальную настройку компонентов, а через модуль Actuator даёт встроенные механизмы проверки работоспособности сервиса и сбора метрик производительности.
Интеграция с асинхронной передачей данных реализована через библиотеку spring-kafka, которая позволяет декларативно настраивать обработчиков сообщений с помощью аннотаций, управлять ошибками обработки и автоматически направлять проблемные сообщения, вызывающие сбои, в отдельный топик ошибочных сообщений (Dead Letter Topic). Настройка форматов передачи данных (например, JSON или Avro) вынесена в конфигурационные файлы, что позволяет менять формат сообщений без изменения программного кода потребителей.
В качестве распределённой платформы для потоковой передачи данных выбрана Apache Kafka 3.x, основанная на принципе постоянного журнала событий. В отличие от традиционных очередей сообщений (например, RabbitMQ), где данные удаляются сразу после прочтения, данная система сохраняет сообщения на диске в течение заданного времени. Это позволяет потребителям при необходимости перечитывать исторические данные, что является фундаментом для архитектуры, основанной на источнике событий (Event Sourcing). Разделение топиков на партиции обеспечивает параллелизм обработки: несколько экземпляров сервиса могут одновременно читать данные из разных частей потока. Начиная с версии 3.x, платформа использует собственный механизм консенсуса KRaft, который заменяет внешнюю зависимость от Apache ZooKeeper. Метаданные кластера теперь хранятся внутри самого брокера, что упрощает его развёртывание и обслуживание.
Для хранения агрегированного текущего состояния помещений, полного журнала сырых событий с датчиков и зарегистрированных тревожных сигналов применяется реляционная СУБД PostgreSQL 16. Поддержка формата JSONB позволяет гибко хранить полуструктурированные метаданные, а механизм оптимистичной блокировки (через поле версии записи) предотвращает конфликты при одновременном обновлении данных несколькими сервисами.
Развёртывание локального стенда разработки осуществляется с помощью инструмента Docker Compose для оркестрации контейнеров. С его помощью все компоненты системы (брокер сообщений, СУБД и четыре микросервиса) запускаются единой командой. Это гарантирует идентичность среды разработки на разных рабочих станциях и упрощает интеграцию в процессы непрерывной интеграции и доставки (CI/CD).Таблица 2 содержит сводку по отвергнутым альтернативам с обоснованием отказа.

Выводы по разделу
По результатам обзора для задачи мониторинга параметров среды в помещениях целесообразно строить систему на открытом ПО с асинхронной архитектурой. SCADA-системы избыточны для офисных и коммерческих объектов и плохо масштабируются. Облачные платформы скрывают логику обработки за проприетарными сервисами и создают зависимость от вендора. Apache Kafka в качестве транспорта событий даёт персистентный лог с replay, упорядоченную доставку внутри помещения и возможность наращивать потребителей без переделки логики. Стек Kotlin, Spring Boot, Kafka, PostgreSQL и Docker Compose отвечает требованиям задания; проектирование архитектуры на его основе изложено в следующем разделе.
Из обзора вытекает набор конкретных архитектурных решений: Kafka с партиционированием по room_id в качестве транспорта, Event Sourcing для хранения и восстановления состояния, разделение записи и чтения (CQRS), DLQ для обработки ошибочных сообщений и идемпотентная вставка по event_id на стороне потребителя. Реализация этих решений описана в следующих разделах.

2.2 Декомпозиция на сервисы и их взаимодействие
Архитектура системы построена по микросервисному принципу: каждая логически обособленная задача выделена в отдельный сервис со своим процессом, конфигурацией и независимым жизненным циклом. Такое разбиение позволяет развивать, тестировать и масштабировать компоненты по отдельности. Система включает четыре основных сервиса и вспомогательное приложение-эмулятор датчиков.
Сервис приёма событий (event-ingestion-service) — единственная точка входа для данных от датчиков. Он принимает HTTP-запросы с телом в формате JSON, проверяет наличие обязательных полей и допустимость типа датчика, после чего публикует валидное событие в брокер сообщений. Сервис не хранит собственного состояния и может быть размножен горизонтально за балансировщиком нагрузки.
Сервис агрегации состояния (state-aggregation-service) читает поток событий из брокера и выполняет две операции: сохраняет каждое событие в полный журнал (таблица sensor_events) и обновляет агрегированное состояние помещения (таблица room_states). Перед записью проверяется уникальность идентификатора события, что исключает дублирование при повторной доставке. После обновления состояния сервис публикует его актуальный снимок в отдельный канал сообщений, доступный для внешних потребителей. Этот же сервис реализует механизм повторного воспроизведения: по команде администратора он очищает таблицу состояний и пересчитывает её заново из полного журнала событий.
Сервис обнаружения аномалий (anomaly-detection-service) подписан на тот же поток событий, что и сервис агрегации, но входит в отдельную группу потребителей. При поступлении события он проверяет его значение по набору пороговых правил, загруженных из конфигурационного файла. Если значение выходит за допустимый диапазон, сервис создаёт запись об оповещении в БД и публикует её в канал оповещений. Сервис не хранит промежуточного состояния и масштабируется горизонтально.
Сервис предоставления данных (query-service) реализует REST-интерфейс для чтения. Он обращается только к БД и не взаимодействует с брокером сообщений. Через него внешние клиенты получают текущее состояние помещений, историю показаний за заданный период и список оповещений с возможностью фильтрации. Сервис также не хранит собственного состояния.
Эмулятор датчиков (iot-simulator) — вспомогательное приложение, не входящее в продуктивный контур. Оно генерирует поток правдоподобных событий с настраиваемыми параметрами (количество помещений, типы датчиков, частота отправки, диапазоны значений) и отправляет их в сервис приёма по HTTP. Эмулятор используется для разработки, отладки и проведения тестов.

2.3 Структура потоков сообщений
Взаимодействие между сервисами осуществляется через именованные каналы (топики) брокера сообщений. Каждый канал предназначен для определённого типа данных и имеет фиксированный набор издателей и подписчиков. Ключом разделения (партиционирования) во всех каналах служит идентификатор помещения, что гарантирует обработку событий одного помещения строго одним экземпляром потребителя в рамках группы.

Таблица 6 — Каналы сообщений брокера
Канал	Издатель	Подписчики	Содержимое
sensor-raw-events	Сервис приёма	Агрегация, обнаружение аномалий	Сырое событие датчика
sensor-raw-events.DLT	Обработчик ошибок потребителя	Ручной разбор	Событие, не обработанное после повторных попыток

Каналы с суффиксом «.DLT» (от англ. Dead Letter Topic — канал недоставленных сообщений) служат для изоляции событий, которые не удалось обработать после заданного числа повторных попыток. Такие события не блокируют обработку остальных данных в разделе и могут быть проанализированы вручную.
Два основных сервиса-подписчика — агрегации и обнаружения аномалий — входят в разные группы потребителей. Это означает, что каждый из них получает полную копию потока и обрабатывает его независимо. Внутри одной группы разделы канала распределяются между экземплярами сервиса: при добавлении второго экземпляра часть разделов автоматически передаётся ему, что увеличивает пропускную способность без изменения логики.
Издатели настроены на подтверждение записи всеми репликами брокера (режим acks=all) и работают в идемпотентном режиме, что исключает появление дубликатов при повторных попытках отправки на транспортном уровне. Потребители фиксируют смещение (offset) только после успешной обработки события, что обеспечивает гарантию доставки «как минимум один раз» (at-least-once). Защита от дублирования на прикладном уровне обеспечивается проверкой уникальности идентификатора события в БД (подробнее — в подразделе 2.4).

2.4 Модель данных
Все данные системы хранятся в реляционной СУБД PostgreSQL. Схема БД принадлежит сервису агрегации состояния и разворачивается автоматически при первом запуске с помощью инструмента миграций Flyway. Остальные сервисы используют ту же базу: сервис обнаружения аномалий записывает оповещения, а сервис предоставления данных обращается к ней только на чтение.
Схема включает три таблицы, каждая из которых отвечает за свою область данных.
Таблица room_states хранит последнее агрегированное состояние каждого помещения. Первичным ключом служит идентификатор помещения (room_id). Поля temperature, humidity, co2, smoke, motion и light содержат последнее известное значение соответствующего типа датчика. Поле updated_at фиксирует время последнего обновления, а поле version — счётчик версий для механизма оптимистичной блокировки. При поступлении нового события сервис агрегации обновляет только то поле, которое соответствует типу датчика в событии, и увеличивает version на единицу. Если между чтением и записью другой поток успел изменить запись (version не совпадает), фреймворк объектно-реляционного отображения выбрасывает исключение, и попытка повторяется.
Таблица sensor_events — полный журнал событий, на котором строится модель журналирования событий, описанная в подразделе 1.4. Каждая запись содержит автоинкрементный первичный ключ (id), уникальный идентификатор события (event_id), идентификаторы помещения и датчика (room_id, sensor_id), тип датчика (sensor_type), числовое значение показания (value) и временную метку (recorded_at). Ограничение уникальности на поле event_id обеспечивает идемпотентность: при повторной доставке одного и того же события попытка вставки завершится отказом, и дублирования не произойдёт. Составной индекс по паре (room_id, recorded_at) ускоряет выборки истории показаний за заданный временной интервал.
Таблица alerts хранит зарегистрированные оповещения. Каждая запись содержит автоинкрементный первичный ключ (id), уникальный идентификатор оповещения (alert_id), идентификатор помещения (room_id), тип датчика (sensor_type), наименование сработавшего правила (rule_name), уровень критичности (severity), текстовое описание (message), значение показания, вызвавшее срабатывание (triggering_value), время возникновения (triggered_at) и время разрешения (resolved_at, допускает пустое значение). Индекс по паре (room_id, resolved_at) ускоряет фильтрацию активных оповещений по конкретному помещению.

2.5 Механизмы отказоустойчивости
Распределённая система состоит из нескольких независимых процессов, каждый из которых может временно выйти из строя: перезапуск сервиса, кратковременная недоступность БД, сетевой разрыв между сервисом и брокером сообщений. Проектные решения, описанные ниже, направлены на то, чтобы ни один из этих сценариев не приводил к потере данных или неконсистентному состоянию.
Повторные попытки и очередь недоставленных сообщений. При ошибке обработки события потребитель не отбрасывает его, а повторяет попытку с фиксированной задержкой. Если после заданного числа попыток (в текущей конфигурации — три, с интервалом в одну секунду) обработка по-прежнему завершается ошибкой, событие автоматически перенаправляется в канал недоставленных сообщений (DLT). Это позволяет изолировать «отравленное» событие: оно не блокирует обработку остальных событий в данном разделе канала и доступно для последующего ручного анализа. Механизм реализован на уровне конфигурации потребителя и не требует изменения бизнес-логики обработки.
Идемпотентный издатель. На стороне отправки сообщений включён идемпотентный режим издателя: при разрыве соединения с брокером издатель повторяет отправку, но брокер отсеивает дубликаты по внутреннему идентификатору последовательности. Тем самым транспортный уровень гарантирует отсутствие дублей в канале даже при сетевых сбоях.
Идемпотентный потребитель. На прикладном уровне защита от дублирования обеспечивается ограничением уникальности на поле event_id в таблице sensor_events (см. подраздел 2.4). Перед вставкой события потребитель проверяет, существует ли запись с таким идентификатором. Если запись уже есть, повторная вставка пропускается. Это покрывает сценарий, при котором потребитель успел записать событие в БД, но не успел зафиксировать смещение в брокере до перезапуска: при повторной доставке того же события дублирования не произойдёт.
Пересчёт состояния из журнала событий. Если таблица агрегированного состояния помещений по какой-либо причине оказалась повреждена или рассогласована, её можно полностью восстановить из полного журнала событий (таблица sensor_events). Для этого сервис агрегации предоставляет административный эндпоинт, при вызове которого происходит следующая последовательность действий:
•	приостановка приёма новых сообщений из брокера;
•	очистка таблицы агрегированного состояния;
•	последовательный перебор всех записей журнала с пересчётом состояния каждого помещения;
•	возобновление приёма сообщений.
Источником истины при пересчёте служит БД, а не брокер, поскольку повторное чтение из брокера столкнулось бы с проверкой идемпотентности и пропустило бы ранее обработанные события. Эндпоинт защищён базовой аутентификацией и доступен на отдельном порту.

В разделе описана программная реализация четырёх микросервисов, составляющих распределённую систему обработки IoT-событий: сервиса приёма событий, сервиса агрегации состояния, сервиса обнаружения аномалий и сервиса предоставления данных. 3.1 Структура проекта
Проект организован как многомодульная сборка на основе системы автоматизации Gradle с использованием языка описания сценариев Kotlin DSL. Корневой проект содержит общие настройки (версии зависимостей, параметры компиляции), а каждый сервис оформлен в виде отдельного подмодуля со своим набором зависимостей, конфигурационными файлами и точкой входа.
Все сервисы построены на основе фреймворка Spring Boot 3.x и написаны на языке Kotlin. Конфигурация каждого сервиса вынесена в файл application.yml, что позволяет изменять параметры (адреса брокера и БД, названия каналов, порты) без перекомпиляции. Схема БД разворачивается автоматически при первом запуске сервиса агрегации с помощью инструмента миграций Flyway: SQL-скрипт, описывающий создание таблиц и индексов, хранится в каталоге ресурсов сервиса и применяется при запуске.

3.2 Сервис приёма событий
Сервис приёма событий реализует единственную точку входа для данных от датчиков — HTTP-эндпоинт POST /events. При поступлении запроса выполняется валидация тела: проверяются наличие обязательных полей (идентификатор помещения, идентификатор датчика, тип датчика, значение показания), допустимость значения перечисляемого типа sensor_type и корректность формата временной метки. Если метка времени отсутствует, сервис подставляет текущее серверное время.
Валидное событие преобразуется в сообщение и публикуется в канал sensor-raw-events брокера сообщений. Ключом сообщения служит идентификатор помещения (room_id), что обеспечивает попадание всех событий одного помещения в один раздел канала. Издатель настроен в идемпотентном режиме с подтверждением всеми репликами (acks=all). При невалидном запросе сервис возвращает HTTP-ответ с кодом 400 и описанием ошибки.
Сервис не хранит состояния и не обращается к БД. Его можно масштабировать горизонтально, разместив несколько экземпляров за балансировщиком нагрузки.
3.3 Сервис агрегации состояния
Сервис агрегации — центральный компонент системы. Он входит в группу потребителей state-aggregation и читает события из канала sensor-raw-events. При поступлении каждого события выполняется следующая последовательность действий.
Последовательность обработки одного события включает четыре шага.
1.	Проверка идемпотентности: сервис проверяет, существует ли в таблице sensor_events запись с таким же event_id. Если запись найдена, обработка прекращается — событие уже было обработано ранее, повторная вставка пропускается.
2.	Сохранение в журнал: если событие новое, оно записывается в таблицу sensor_events (полный журнал событий).
3.	Обновление агрегированного состояния: обновляется соответствующее поле в таблице room_states. Если записи для данного помещения ещё нет, она создаётся; если есть — обновляется только поле, соответствующее типу датчика (например, temperature). Счётчик версий (version) увеличивается на единицу.
4.	Публикация снимка состояния: актуальное состояние помещения отправляется в канал room-state-events, доступный для внешних подписчиков.
Механизм повторного воспроизведения реализован в виде административного эндпоинта POST /admin/replay, защищённого базовой аутентификацией и доступного на отдельном порту (8082). При вызове этого эндпоинта сервис выполняет следующую последовательность действий.
•	приостановка приёма новых сообщений из брокера (остановка слушателей);
•	очистка таблицы room_states (удаление всех агрегированных состояний);
•	последовательный перебор всех записей таблицы sensor_events, упорядоченных по метке времени recorded_at, с пересчётом агрегированного состояния каждого помещения;
•	возобновление приёма сообщений из брокера.
Источником истины при пересчёте служит БД, а не брокер, поскольку механизм идемпотентности (проверка event_id) пропустил бы повторно полученные из брокера события. Ход выполнения операции отслеживается через метрики: общее число вызовов, количество обработанных событий, длительность и признак выполнения в текущий момент.
3.4 Сервис обнаружения аномалий
Сервис обнаружения аномалий подписан на канал sensor-raw-events в составе отдельной группы потребителей (anomaly-detection) и получает полную копию потока событий независимо от сервиса агрегации.
Пороговые правила описаны в конфигурационном файле anomaly-rules.yml и загружаются при запуске сервиса. Каждое правило содержит следующие параметры:
•	наименование правила;
•	тип датчика, к которому применяется правило;
•	условие срабатывания (значение больше или меньше порога);
•	пороговое значение;
•	уровень критичности (INFO, WARNING, CRITICAL).
Изменение правил не требует перекомпиляции — достаточно отредактировать файл и перезапустить сервис.
При поступлении каждого события механизм проверки (RuleEngine) отбирает правила, соответствующие типу датчика в событии, и проверяет условие. Если значение показания удовлетворяет условию хотя бы одного правила, формируется запись об оповещении. Запись сохраняется в таблицу alerts базы данных и одновременно публикуется в канал alert-events брокера сообщений. Канал оповещений доступен для подключения будущего сервиса уведомлений (отправка электронной почты, SMS), который в текущей версии не реализован.
Сервис не хранит промежуточного состояния: каждое событие обрабатывается независимо от предыдущих. Это позволяет масштабировать его горизонтально — дополнительные экземпляры получат свои разделы канала и будут проверять правила параллельно.

3.6 Эмулятор датчиков
Эмулятор датчиков — самостоятельное приложение на Kotlin и Spring Boot, не входящее в продуктивный контур системы. Оно используется при разработке, отладке и тестах для генерации реалистичного потока событий.
Эмулятор создаёт настраиваемое количество виртуальных помещений, в каждом из которых размещены датчики заданных типов. С заданным интервалом генерируются показания со случайным значением в пределах реалистичного диапазона (например, температура 18–30 °C, влажность 30–70 %, CO₂ 400–2000 ppm). Периодически значения намеренно выводятся за пределы нормы для срабатывания механизма обнаружения аномалий.
Параметры генерации (число помещений, типы датчиков, частота отправки, адрес сервиса приёма) задаются в конфигурационном файле application.yml и могут быть переопределены через переменные окружения при запуске контейнера.

Модульные тесты охватывают две ключевые области бизнес-логики.

•	срабатывание при условии «больше порога»;
•	срабатывание при условии «меньше порога»;
•	отсутствие срабатывания при нормальном значении;
•	фильтрация правил по типу датчика;
•	корректность выбора уровня критичности;
•	загрузка конфигурации правил.

3.9 Подготовка нагрузочного тестирования
Для оценки пропускной способности и времени отклика системы подготовлены сценарии нагрузочного тестирования на основе инструмента k6. Сценарии хранятся в каталоге loadtest/ репозитория проекта.
Первый сценарий (k6-constant.js) моделирует постоянную нагрузку с заданным числом событий в секунду (по умолчанию 200, параметризуется через переменную окружения RPS) в течение пяти минут. Измеряются перцентили времени отклика HTTP-эндпоинта POST /events (p50, p95, p99) и доля ошибок.
Второй сценарий (k6-burst.js) моделирует пиковую нагрузку: разогрев при 200 событиях в секунду, затем всплеск до 5000 событий в секунду на протяжении 30 секунд с последующим возвратом к 200 событиям в секунду. Цель — проверить, что система не теряет события при кратковременном превышении штатной нагрузки и способна обработать накопленную очередь после снижения интенсивности.
Сквозная задержка (от момента отправки события до обновления состояния помещения в БД) оценивается путём сравнения временной метки в теле события с полем updated_at в таблице room_states. В процессе прогона через Prometheus снимаются следующие технические метрики:
•	расход оперативной памяти JVM (heap usage);
•	отставание потребителя от конца канала (consumer lag);
•	частота и длительность сборки мусора (GC pauses);
•	число HTTP-запросов в секунду и доля ошибок;
•	перцентили времени отклика (p50, p95, p99).
На момент написания настоящей работы инфраструктура нагрузочного тестирования подготовлена: скрипты написаны, инструкции запуска задокументированы (loadtest/README.md), шаблон отчёта создан (docs/loadtest-results.md). Результаты прогонов будут дополнены по мере проведения экспериментов.
