# ADR-004: План доработки кода и сервисов до защиты

**Статус:** Принято
**Дата:** 2026-05-03

## Контекст

Минимальный конвейер работает: симулятор → ingestion → Kafka → aggregation/anomaly → PostgreSQL → query API. Этого недостаточно для защиты по заданию: нет тестов, нет явного механизма replay, не подтверждена пропускная способность и поведение под отказами. Этот ADR фиксирует, что ещё нужно сделать в коде и сервисах в рамках scope ВКР. Раздел БЖД, текст пояснительной записки и иллюстративный материал в этом плане не учитываются.

## Решение

Работа делится на четыре последовательных блока. Каждый можно мержить отдельно.

### Блок 1. Тестирование

Цель — закрыть юнит-тестами правила и аггрегацию, интеграционными — критический путь от HTTP до БД.

- Юнит-тесты:
  - `RuleEngine` — срабатывание `GREATER_THAN`/`LESS_THAN`, отсутствие срабатывания, фильтр по типу датчика, выбор `severity`
  - `RoomStateAggregator` — обновление поля по типу датчика, идемпотентность по `event_id`, инкремент `version`
- Интеграционные тесты на Testcontainers (Kafka + PostgreSQL):
  - **End-to-end ingestion:** POST в event-ingestion → событие появилось в `sensor-raw-events` → state-aggregation записал в `sensor_events` и обновил `room_states` → query-service отдал свежее состояние
  - **Anomaly path:** event с превышением порога → запись в `alerts` → событие в `alert-events`
  - **Идемпотентность:** одинаковый `event_id` дважды → одна строка в `sensor_events`, `version` инкрементировался один раз
  - **Replay:** truncate `room_states` + сброс offset → пересчитанное состояние совпадает с эталоном

Технологии: JUnit 5, Spring Boot Test, Testcontainers (`KafkaContainer`, `PostgreSQLContainer`), `EmbeddedKafka` не использовать — реальный контейнер ближе к проду.

### Блок 2. Замыкание Event Sourcing

Цель — сделать replay не «инструкцией в README», а явной операцией системы.

- Admin-эндпоинт `POST /admin/replay` в `state-aggregation-service`: транзакционно truncate `room_states` + reset offset consumer-group до `earliest` + ребаланс. Результат: возврат количества переигранных событий и нового `version` по комнатам.
- Защитить эндпоинт actuator-style ограничением (отдельный профиль/порт или basic auth — проще basic auth).
- Метрика `replay_in_progress` (Gauge) и `replay_events_processed_total` (Counter).

### Блок 3. Отказоустойчивость

Цель — подтвердить, что система переживает падение отдельных компонентов и не теряет данные.

- **Retry + DLQ.** Для consumer-ов state-aggregation и anomaly-detection включить `DefaultErrorHandler` со `FixedBackOff` (3 попытки с задержкой) и публикацию неперевариваемых сообщений в `*.DLT` через `DeadLetterPublishingRecoverer`. Так poison message не блокирует partition.
- **Producer-устойчивость.** Уже есть `acks=all` и идемпотентность; добавить `enable.idempotence=true` явно, `retries=Integer.MAX_VALUE`, `delivery.timeout.ms=120000`.
- **Сценарии тестирования отказоустойчивости** (отдельный `docs/resilience-tests.md` или раздел `docs/architecture.md`): остановка PostgreSQL во время записи, остановка Kafka, kill state-aggregation в середине обработки, рестарт ingestion. На каждом сценарии — что происходит, какие гарантии сохраняются, как восстанавливается.
- Фиксация поведения тестом: `@Testcontainers` сценарий, который убивает PG-контейнер и проверяет, что при возврате всё доезжает.

### Блок 4. Нагрузочное тестирование

Цель — получить цифры пропускной способности и задержки для пояснительной записки (но сами тесты — это код).

- Инструмент: k6 или Gatling. k6 проще: один JS-файл, без JVM. Положить под `loadtest/`.
- Сценарии:
  - **Constant load:** 200, 500, 1000 events/sec в течение 5 минут, измерить p50/p95/p99 на POST `/events` и end-to-end задержку (от POST до появления записи в `room_states` — измеряется через сравнение `event.timestamp` с `room_states.updated_at` в логах)
  - **Burst:** 5000 events/sec в течение 30 секунд, проверить что система не теряет события и догоняется
- Метрики снимать через Prometheus (актуатор + JVM + Kafka client) и сохранять в `docs/loadtest-results.md`.
- Параллельно: масштабирование. Запустить два экземпляра state-aggregation в одной consumer-group и убедиться, что lag падает быстрее.

### Порядок и зависимости

Блок 1 сначала — он защищает от регрессий при следующих правках. Блок 2 даёт явный артефакт «Event Sourcing работает». Блок 3 строится поверх 1+2. Блок 4 — последний, чтобы цифры были репрезентативны для финальной системы.

## Что вне этого плана

- ML-детекция аномалий (только пороговые правила).
- Аутентификация публичного API сложнее basic auth.
- Авто-resolved алерты (поле `resolved_at` остаётся, но логика закрытия не реализуется).
- Управление актуаторами / обратное направление команд.
- Mobile/web UI; вместо него — Grafana (см. ADR-005).
